| U3 dlq replay — a dead letter gets a second chance | U3 | 2026-08-01 | **pass** | Verdict recorded by memo (darchitect) via validate/dlq-replay.md, local and cloud. `--replay` puts a message back into at-least-once delivery and takes it off the DLQ — a MOVE, ack after republish, so a crash duplicates rather than loses. Topic replay was the decision: a topic fans out but a dead letter belongs to ONE subscriber, and Pub/Sub has no inject-into-one-subscription API, so the message returns through the topic carrying `tako-replay-to` and every other subscriber acks and drops. Riding the real broker is what makes a failed replay land back on the DLQ instead of vanishing into the CLI — proven live: replay → redeliver → fail → back on the DLQ with a NEW id, same payload. Dead letters also gained addressable ids (Pub/Sub `messageId`, file stem locally, git-style unique prefixes); the cloud path previously held only a per-pull `ackId`, invalid by the time you could type it. **The gate caught a bug that made the entire local half dead on arrival:** the dispatcher writes `payload` as raw JSON, both readers declared it as `backends.DeadLetter` whose `[]byte` `encoding/json` fills only from base64, so every real record failed to unmarshal and was skipped silently — `tako dlq --local` reported an empty DLQ over a directory full of files, and local replay could never have run. The tests passed because the fixture helper marshalled `backends.DeadLetter` directly, a shape nothing in production writes: four tests exercising a file format that does not exist. The on-disk shape is now a named type used by the writer and by an exported decoder both readers call, with a regression test that produces a REAL dead letter and decodes the actual file. Same family as the metrics resource-type miss — a fixture that constructs its own input tests the fixture as much as the code. |
